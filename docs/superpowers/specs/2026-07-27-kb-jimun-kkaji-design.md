## 1. 개요

### 1-1. 서비스

| | |
|---|---|
| 서비스명 | **「지문까지」** |
| 과제명 (참가신청서) | **「지문까지」 — 메뉴를 대신 걷는 실행형 AI 에이전트** |
| 부제 | 말하면, 지문까지 데려다 드립니다 |
| 발표 제목 | **"안내하지 않습니다. 대신 합니다."** |
| 한 줄 정의 | 무엇을 눌러야 할지 몰라도, **어느 계열사인지 몰라도**, 말하면 AI가 메뉴를 대신 걸어 실행 직전까지 준비하고, 사용자는 지문만 찍는 **실행형 에이전트** |
| **참가 형태** | **개인** |

### 1-2. 대회 제약

- 제출물: 참가신청서 + 기술설명서(PPT) + 프로토타입(구현코드) → zip 1개
- 예선 배점 100점 — 문제정의 15 / 활용가능성 15 / **창의성·효과 20** / **기술적정성 20** / 개발계획 15 / 실현가능성 15
- 추가 설명용 **동영상 제출 가능**
- GitHub 링크 제출 가능하나 **접수기간 이후 수정·변경 이력 확인 시 심사 제외**
- 참가신청서에 **AI 활용 내용 신고표** 작성 필요 (도구별 반영 정도 체크)
- 서약서: 외부 생성형 AI 도구 사용 허용, 이용약관·라이선스·저작권 준수 조건

### 1-3. 왜 이 주제인가

KB 역대 1~7회 + 2026년 필드 + 타 대회(우리·신한라이프·금융보안원·NH) 수상작을 전수 대조한 결과:

- KB 역대 대화형 과제 5건(LiivBERT·KB:OT·상담사지원·권익보호에이전트·민원작성)은 **전부 답변 생성에서 멈춤**
- 7회 입상작 5개도 **판단·모니터링·추천**에 그침
- 8회 현직자 Pick 6개도 **전부 제안·추천·안내**
- → **"은행 업무를 대신 실행"은 KB에서 0건**
- → **"계열사 경계를 넘어 라우팅"도 0건**

## 2. 문제 정의

### 2-1. 3단계 구조

| 단계 | 문제 | 근거 |
|---|---|---|
| **[1]** 앱에서 기능을 못 찾는다 | 기능이 없어서가 아니라 묻혀 있어서 | KB 앱 4대 은행 실측 **최하위권** |
| **[2]** 챗봇에 물어도 "찾을 수 없어요" | intent 분류는 학습된 것만 처리 | 현직 챗봇 기획자 증언 |
| **[3]** 전화해도 ARS 미로 + 10~20분 대기 | | 60대+ 대면·전화 의존 **80.7%** |

**[1] 근거 원문**
> KB국민은행 — 진입 경로가 복잡합니다. 간편 모드 전환을 위해 검색창에 직접 입력하거나 화면 하단까지 내려야 합니다. 진입 후에도 글자 크기와 화면 구성은 기존과 크게 달라지지 않았으며, **"통합거래내역" 같은 용어는 여전히 직관적이지 않습니다.**

**[1] 자체 실측 (2026-07-27, obank.kbstar.com 개인뱅킹 전체 메뉴 트리)**

**① 자동이체 하나 끊는 데 관련 메뉴가 16개다**
```
자동이체통합관리 · 자동이체 · 자동이체내역 조회/해지/변경 · 자동이체 등록
자동이체결과확인증 · 자동이체 서비스 · 자동이체통합관리 서비스란?
자동이체 계좌변경 · 자동납부 계좌조회/출금계좌 변경 · 자동납부 변경신청결과 조회
자동송금 계좌조회/출금계좌 변경 · 자동송금 변경신청결과 조회 · 자동납부 등록/해지
일임형 ISA 자동이체 · 외화자동이체 · 자동이체관리
```
**용어가 세 갈래로 갈린다 — 자동이체 / 자동납부 / 자동송금.** 일반 사용자가 이 셋의 차이를 알 방법이 없다.

**② 지적된 용어가 실재한다** — 실물 명칭은 **「다른금융 통합거래내역조회」**로, 지적된 것보다 더 길다.

**③ 메뉴 뎁스** (페이지 `<title>`의 브레드크럼 실측)
```
계좌조회   개인뱅킹 | 조회 | 계좌조회 | 국민은행 계좌조회 | 예금      = 5뎁스
제증명     개인뱅킹 | 뱅킹관리 | 제증명발급 | 예금잔액증명서         = 4뎁스
자동이체   개인뱅킹 | 이체 | 자동이체 | 자동이체내역 조회/해지/변경   = 4뎁스
```

**④ 어르신전용 콜센터가 이미 존재한다 — 1644-3308** (외국인전용 1599-4477 별도 운영)
→ 전화 채널은 새로 만드는 것이 아니라 **이미 있는 채널을 바꾸는 제안**이다.

### 2-2. ★ 왜 이 문제는 앱 리뷰에 안 나타나는가

KB스타뱅킹 Google Play 저평점 리뷰 88건(400건 스캔) 분류 결과:

| 유형 | 건수 |
|---|---|
| **인증·로그인** | **51 / 88 (58%)** |
| 속도·오류 | 9 |
| 메뉴·탐색 | 6 (7%) |
| UI·디자인 | 4 |

> "인증서 재발급 뜨길래 진행하는데 **안면인식 오류 진짜 심각합니다.** 토스 앱에서 할땐 오류없이 잘됐었는데 **국민만 유독 안돼서**…"
> "KB국민인증서 발급시 얼굴인식이 전혀안됨… **해결방법은 지점에 찾아가는 방법 밖에 없다고**"

**리뷰의 최대 불만은 인증이고, 이는 본 과제의 스코프 밖이다**(규제·보안 영역). 그렇다면 [1]단계 근거는 어디에 있는가?

> **앱 리뷰는 화가 난 사람이 쓴다. 인증이 실패하면 화가 난다.
> 그런데 메뉴를 못 찾으면 화가 나기보다 포기하고 전화를 건다.
> 그래서 이 문제의 증거는 앱 리뷰가 아니라 콜센터에 있다.**

- 지식iN "상담원 연결 답답" **3,695건+**
- 콜센터 증언: "고객들은 **자신이 뭘 묻고 싶은지 모르기 때문에** 전화한다"
- 실측 평가: KB 앱 간편모드 진입 경로 복잡, "통합거래내역" 등 용어 장벽

→ **리뷰에 없다는 사실 자체가 논거다.** "리뷰엔 별로 없던데요?"라는 반론에 대한 답이 이미 준비돼 있다.

### 2-3. 근본 원인

> "고객들은 **자신이 뭘 묻고 싶은지 모르기 때문에** 전화한다"
> "현재 정책은 교육과 접근성 개선에 치중돼 있으나, 실제 어려움은 **'이해'를 넘어선 '실행' 단계**에 있어 괴리가 발생한다"
> "**기술 성숙도 부족이 아닌 설계 미흡**"

지금의 챗봇·ARS는 **정확한 명령**을 전제한다. 그런데 도움이 필요한 사람일수록 정확한 명령을 할 줄 모른다.

### 2-4. 핵심 명제

> **모든 은행이 "더 잘 안내하는 법"을 고민한다. 우리는 안내를 없앤다.**

### 2-5. 보조 근거

- 은행 점포 7,835개(2012) → **5,523개(2025)**
- 60대 이상 모바일 금융 이용 18.7% ↔ 전체 은행 업무의 84.6%가 인터넷뱅킹

## 3. 사용자와 스코프

### 3-1. 사용자

| | 누구 | 채널 | 무엇이 막나 |
|---|---|---|---|
| **1차 (메인)** | 앱은 쓰지만 **안에서 길을 잃는 사람** (20~50대) | 앱 내 | 5뎁스 미로, 용어 장벽 |
| 2차 (시연 1개) | 앱을 못 쓰는 고령층 | **전화** | ARS 미로 |

**설계 원칙:** 앱 진입장벽(설치·본인인증·로그인)은 **우리가 푸는 문제가 아니라고 명시적으로 선언한다.** 고령층은 앱이 아니라 전화로 같은 에이전트에 닿는다.
→ "앱을 잘 쓰게 만들겠다"가 아니라 **"앱을 못 써도 같은 에이전트에 닿게 하겠다"**

### 3-2. 스코프

| ✅ 한다 | ❌ 안 한다 |
|---|---|
| 자연어 → 앱 기능 실행 준비 (Function Calling) | 앱 설치·본인인증·로그인 개선 |
| 모호하면 되묻기 | 새 인증 방식 발명 — 기존 지문/PIN 그대로 |
| 실행 전 부수효과 경고 | AI가 최종 실행 — 방아쇠는 항상 사람 |
| 왜 그런지 근거 설명 | 개인정보를 LLM에 전송 |
| 전화 채널 시연 1개 | **상품 추천·판매** ← KB 4연속 탈락 라인 |

**마지막 줄 근거:** KB에서 자산관리·추천·개인화 과제는 4연속 본선 탈락(I-Diary 6회 · Just Fit it 7회 · OHAE 3회 · Zero-Shot 투자성향 3회). 이 서비스는 **사용자가 이미 하려는 일을 대신 할 뿐, 새로운 상품을 권하지 않는다.**

### 3-3. 업무 범위 — 2계층 구조

**5개만 하드코딩한 것은 통합 서비스가 아니라 데모 5개다.** 심사위원이 6번째를 물으면 무너진다. 따라서 계층을 나눈다.

#### Layer 1 — 전체 커버리지 (라우팅) ★ 이것이 "통합"이다

KB 3사 메뉴 트리 **전체**를 크롤링해 임베딩 인덱스로 만든다. 어떤 발화가 들어와도 **"그건 여기 있습니다"**를 답한다. 사용자는 계열사 경계를 몰라도 된다.

| 계열사 | 고유 메뉴 항목 (2026-07-27 실측) |
|---|---|
| KB국민은행 개인뱅킹 | **657** (동사가 붙은 실제 업무 **227**) |
| KB국민카드 | **1,197** |
| KB증권 | **801** |
| **합계** | **약 2,655** |

→ **"찾을 수 없어요"가 원천적으로 불가능해진다.**

#### Layer 2 — 조회·답변 (40~50개)

더미 데이터를 조합해 바로 답한다. **실행형과 달리 부수효과 로직이 필요 없어 싸게 대량 생산된다.** 실행과 같은 층에 두면 손해다.

#### Layer 3 — 실행 (12~15개)

부수효과 경고 + 실행 직전 준비 + 지문 인증. 수작업 비용이 높으므로 빈도 높은 것부터.

```
기존 챗봇   학습된 것만 답 → 나머지는 "찾을 수 없어요"
L1          2,655개 전부 안다 → "찾을 수 없어요"가 불가능
L2          40~50개는 조회해서 바로 답한다
L3          12~15개는 아예 대신 실행한다
```

#### ★ 발화 변형 대량 생성 — "최대한 많이 학습"

메뉴명만 임베딩하면 매칭되지 않는다. `자동납부 등록/해지` ↔ *"통신비 자동으로 나가는 거 그만"*의 텍스트 유사도는 거의 0이다.

```
메뉴 1개 → LLM으로 사용자 발화 변형 8개 생성 → 함께 인덱싱

  '자동납부 등록/해지'
   ├ "통신비 자동으로 나가는 거 그만하고 싶어"
   ├ "매달 빠져나가는 돈 막아줘"
   ├ "자동이체 끊는 거 어디서 해?"
   ├ "KT 요금 자동결제 취소"
   └ …

2,655개 × 8 = 약 21,000개 발화 인덱스
```

이는 7-0절 커버리지 검증 루프와 **동일한 파이프라인**이다. 생성 → 인덱싱 → 검증 → 구멍 보강이 한 사이클로 돈다.

**구현 부담:** L1 인덱싱과 발화 생성은 전부 스크립트로 자동화된다. 손으로 만드는 건 L3 실행 툴 12~15개뿐이다. **5개 하드코딩보다 이쪽이 오히려 현실적이다.**

#### 시나리오 카탈로그

| 계열사 | 시나리오 |
|---|---|

| 카드 | 할부기간 변경 / 분할납부 신청 / 한도 변경 신청 / 이메일명세서 신청 |
| 증권 | 잔고증명서 발급 / 금융소득증명서 발급 / **해외주식양도소득내역 발급 ★** |

| 카드 | 결제예정금액 / 이용내역 / 명세서 / **실적충족현황 ★** / 할인한도 / 포인트리 잔액 / 한도 / 예상 할부수수료 / 연회비 |

★ = 시연 영상 5개. **시연은 5개지만 학습·대응 범위는 전체다.**

#### ⚠️ 계열사 경계에 관한 실측 사실

- KB국민은행 개인뱅킹 메뉴에 **신용카드 해지가 없다** (사고신고의 "현금/직불카드"뿐). 사이트 하단에 **"KB국민은행은 KB국민카드의 판매대리·중개업자입니다"** 명시.
- 지식iN 답변자들이 **"KB국민카드(은행 아님)"**라고 계속 교정한다.
- KB스타뱅킹은 **6개 계열사 80여 개 서비스**를 담은 슈퍼앱(MAU 약 1,388만, 은행앱 1위)이지만, 사용자 불만은 여전하다 — *"여전히 개별 앱을 요구하는 경우가 많고 **찾기가 너무 어렵다**"*

> **슈퍼앱은 서비스를 한곳에 모았다. 우리는 입구를 하나로 만든다.**

#### 🔥 같은 목적의 서류가 계열사마다 다른 이름이다

| 목적 | KB국민은행 | KB증권 |
|---|---|---|
| 잔액 증명 | **예금잔액증명서** | **잔고증명서발급** |
| 금융소득 | **금융소득종합과세 조회** | **금융소득증명서발급** |
| 원천징수 | **원천징수영수증발급** | **계좌별과세내역** |

세금 신고 한 번에 은행에서 하나, 증권에서 하나를 떼야 하는데 **이름이 다르다.** 사용자는 둘이 같은 건지 다른 건지도 모른다.

## 4. 시스템 아키텍처

### 4-1. 전체 구조

```
┌ 입구 ────────────────────────────────────────┐
│  A. 앱 대화 UI  (메인)                        │
│  B. 전화 음성   (시연 1개 · 고령층)            │
└──────────────────┬───────────────────────────┘
                   ↓
        ╔══════ PII 경계 ══════╗   ← 이 선을 넘는 개인정보 없음
        ║  ① Understander (LLM) ║
        ║  ⓪ MenuRouter  ───────╫──▶ [Layer 1] 2,655개 메뉴 임베딩 인덱스
        ║       ↓                ║      → 어떤 발화든 "여기 있습니다"
        ║  ② ToolSelector (LLM) ║      → 실행 가능하면 Layer 2로
        ╚═══════════════════════╝
                   ↓  (Layer 2 대상일 때만)
   ③ Resolver → ④ ImpactAnalyzer → ⑤ Preparer
                   ↓
              ⑥ AuthGate  ← 사람이 지문을 찍어야만 통과
                   ↓
            ⑦ Bank Tools (실행)
                   ↓
              ⑧ Audit Log
```

**분기 규칙**
```
발화 → ⓪ MenuRouter (21,000개 발화 인덱스에서 의미 검색)
        ├─ L3 대상 (실행 툴 보유)  → ② ToolSelector → 부수효과 경고 → 실행 준비 → 지문
        ├─ L2 대상 (조회 툴 보유)  → 더미 데이터 조회 → 바로 답변
        └─ L1만                    → "○○ 계열사 > A > B > C 에 있습니다" + [바로가기]
```
L1만으로도 **기존 챗봇의 "찾을 수 없어요"보다 압도적으로 낫다.** 실행까지는 못 해도 **못 찾는 일은 없다.**

### 4-2. 컴포넌트

| # | 이름 | 책임 | LLM? | 개인정보 접근 |
|---|---|---|---|---|
| ⓪ | **MenuRouter** | **2,655개 메뉴 인덱스에서 의미 검색 → 계열사·경로 특정** | 임베딩 | ❌ |
| ① | Understander | 발화 → 의도. 모호하면 되물을 질문 생성 | ✅ | ❌ |
| ② | ToolSelector | 의도 → function call | ✅ | ❌ |
| ③ | Resolver | 별칭 → 실제 ID (`"스마트카드"` → `card_id=3`) | ❌ | ✅ |
| ④ | ImpactAnalyzer | 부수효과 탐지 (자동이체·연계상품·수수료) | ❌ | ✅ |
| ⑤ | Preparer | 실행 계획 생성. **실행은 안 함** | ❌ | ✅ |
| ⑥ | AuthGate | 기존 인증(지문/PIN/강화인증) | ❌ | ✅ |
| ⑦ | Bank Tools | 프로토타입=더미 / 운영=은행 API | ❌ | ✅ |
| ⑧ | Audit Log | 판단 로그 + LLM 전송 페이로드 기록 | ❌ | — |
| — | LLMAdapter | 모델 교체 계층 | — | — |

### 4-3. 세 가지 구조적 보장

**① AI는 실행할 수 없다 (권한 구조)**
`Preparer`는 실행 계획만 반환한다. 실행 함수는 `AuthGate`를 통과한 토큰이 있어야만 호출된다.
→ "AI가 조심한다"가 아니라 **"AI가 호출할 함수 자체가 없다"**

**② 개인정보는 LLM에 갈 수 없다 (경계 구조)**
`Understander`·`ToolSelector`의 입력 타입에 개인정보 필드가 애초에 없다. 실수가 아니라 **타입이 막는다.**

**③ 모델은 교체 가능하다 (어댑터 구조)**
```
LLMAdapter
   ├─ ExternalAdapter   (Phase 0 — 프로토타입)
   ├─ KBGenAIAdapter    (Phase 1 — KB 플랫폼 민감도 라우팅)
   └─ LocalAdapter      (Phase 2 — EXAONE / Solar 온프레미스)
```

### 4-4. 데이터 흐름 예시

```
사용자   "이 카드 없애줘"
[PII Filter]   발화에 개인정보가 섞였으면 마스킹
[① LLM]        의도=CARD_CANCEL, 대상 미지정 → 되물을 질문 생성
[화면]         "어떤 카드 말씀이세요?" + 보유카드 목록(내부 조회, LLM 미경유)
사용자   "스마트카드"
[② LLM]        cancel_card(alias="스마트카드")
[③ Resolver]   alias → card_id=3
[④ Impact]     자동이체 2건 발견 (통신비·넷플릭스)
[⑤ Preparer]   실행계획 생성 — 아직 실행 안 함
[화면]         ⚠️ 경고 + 선택지
[⑥ AuthGate]   지문 🔒
[⑦ 실행]
```

### 4-5. 에러 처리

| 상황 | 처리 |
|---|---|
| 의도 불명확 | 되묻기 최대 2회 → 상담원 연결 |
| 툴 선택 실패 | "처리할 수 없는 요청입니다" + 기존 메뉴 링크 폴백 |
| LLM 타임아웃·장애 | **기존 메뉴 검색으로 폴백** — 서비스가 죽지 않음 |
| 되돌릴 수 없는 작업 | 확인 단계 필수, 건너뛰기 불가 |
| STT 오인식 (전화) | 되풀이 확인 설계가 방어 |
| 부수효과 조회 실패 | **실행 차단.** "확인할 수 없어 진행하지 않습니다" |

**원칙: 모르면 진행하지 않는다.**

### 4-6. Audit Log (데모 핵심 장치)

```
┌ LLM 전송 페이로드
│    "이 카드 없애줘"
│    ⚠ 계좌번호·잔액·성명 미전송 (0건)
├ 판단
│    의도 CARD_CANCEL (신뢰도 0.94)
└ 툴 호출
     get_autopay_list(card_id=3)  →  2건
     prepare_cancel(card_id=3)    →  계획 생성
     ⛔ execute_cancel()  — AuthGate 미통과, 호출 불가
```

*모델 실시간 토글은 기각(로컬 모델을 배포 데모에 넣는 것은 기간상 위험). 어댑터 구조는 코드에 실재시키고, 로컬 모델 대조는 평가 섹션에서 실측한다.*

### 5-2. 전화 (고령층) — 1개

**"이번 달에 돈이 왜 이렇게 나갔지?"**

*송금 시나리오는 채택하지 않음 — 극적이지만 보안 질문을 불러들이고, 고령층 실제 최다 문의는 "내 돈이 어디로 갔는지"다.*

**채널: KB 어르신전용 콜센터 1644-3308** — 이미 존재하는 번호다. 새 채널을 만드는 것이 아니라 **그 번호 뒤의 ARS를 바꾸는 제안**이다.

```

🏦 네, KB국민은행입니다. 무엇을 도와드릴까요?
👤 어… 이번 달에 통장에서 돈이 자꾸 빠져나가는데 뭔지를 모르겠어

👤 응

   두 번째, 케이블 방송. 만 오천 원…
   혹시 안 쓰시는 게 있으실까요?
👤 케이블은 안 봐

```

### 5-3. 고령층 음성 설계 원칙 6가지

| # | 원칙 | 이유 |
|---|---|---|
| ① | 한 번에 하나만 묻는다 | 다중 질문은 혼란 |
| ② | 침묵을 기다린다 (3초+) | 반응이 느리다. 끊으면 대화가 무너진다 |
| ③ | 진행 전 동의를 구한다 | 통제감 |
| ④ | 숫자는 두 번 말한다 | 청력·이해 |
| ⑤ | 되풀이해 확인한다 | **STT 오인식 방어를 겸함** |
| ⑥ | 실행은 기존 인증 | 보안 |

**ChatGPT 음성 모드와의 차이:** 그쪽은 빠르고 자연스러운 대화가 목표다. 고령층에게는 **천천히, 확인하며, 반복하는** 대화가 맞다. **"ChatGPT처럼"이 아니라 "창구 직원처럼"**이다.

**구현:** 실제 전화망 연동은 기간상 무리 → **브라우저 통화 화면 + 실제 마이크·TTS**로 시뮬레이션. 기획서에 "채널 시뮬레이션"이라고 명시한다.

|---|---|
| **LG EXAONE** | 2.4B/7.8B/32B, **function calling 공식 지원**, 32K 컨텍스트 — 본 아키텍처가 Function Calling 기반이라 직결 |
| **Upstage Solar** | **온프레미스 배포 옵션**, 한국어 특화, 환각 최소화 |
| SKT A.X / KT Mi:dm | 자체 7B, 가중치 일부 공개 |
| HyperCLOVA X | 한국어 자연스러움·문화적 맥락 |

### 6-4. 왜 큰 모델이 필요 없는가

본 설계에서 LLM의 역할은 **① 의도 이해 ② 툴 선택** 두 가지뿐이다. **생성이 아니라 분류와 선택**이다.
→ 7B급 소형 모델로도 동작할 가능성이 높으며, 이는 **온프레미스 전환이 현실적이라는 근거**다. 평가 섹션에서 실측으로 확인한다.

### 6-5. 프로토타입이 외부 상용 API를 쓰는 이유 (기획서 수록)

1. **검증 대상이 모델이 아니라 설계이기 때문이다.** 증명하려는 것은 "막연한 발화를 이해하고 스스로 툴을 고르는 구조가 실제로 동작하는가"이며, 모델 성능은 변수이지 논점이 아니다.
2. **개인정보가 전송되지 않아 보안 쟁점이 발생하지 않는다.** 프로토타입 데이터는 전부 더미이며, 운영 설계에서도 PII는 LLM 경계 밖에 있다.
3. **제한된 개발 기간에서 가장 빠른 검증 수단이다.** 온프레미스 모델 구동에 시간을 쓰면 정작 검증해야 할 설계를 만들지 못한다.
4. **교체 비용을 설계로 제거했다.** LLM 호출을 어댑터 계층으로 분리했고, 평가 섹션에서 로컬 모델 대조 실측으로 교체 가능성을 확인했다.
5. 대회 서약서는 외부 도구 사용을 허용하며, **참가신청서 「AI 활용 내용」 표에 사용 모델·도구와 반영 정도를 명시**한다.

## 6-6. 실제 서비스 적용 계획

프로토타입은 **은행 밖에서 은행 안을 흉내 낸 것**이다. 실제 도입에서는 데이터 출처가 전부 바뀐다. 다만 **바뀌는 것은 출처뿐이고, 구조는 바뀌지 않는다.** 그것이 이 설계의 핵심이다.

### 6-6-1. 구성요소별 대응

| 구성요소 | 프로토타입 (지금) | 실제 서비스 | 코드 변경 범위 |
|---|---|---|---|
| **메뉴 카탈로그** | 공개 웹사이트 크롤링 2,656건 | **내부 화면 ID 마스터 · API 레지스트리** | `Collector`만 교체. `MenuNode[]` 스키마는 동일 |
| **발화 변형** | LLM 생성 약 21,000개 | **콜센터 STT 로그 · 챗봇 "찾을 수 없어요" 실패 로그 · 앱 검색어 무결과 로그 · 민원 텍스트** | 인덱스 입력 텍스트만 교체 |
| **조회·실행** | 더미 데이터 | 내부 API 게이트웨이 / 전문 인터페이스 | 각 도구의 `run()` **본문만** 교체 |
| **본인 인증** | 화면 버튼 | 기존 지문·PIN·ARS·강화인증 | `AuthGate` 토큰 발급처만 교체 |
| **LLM** | 외부 상용 API | KB GenAI 플랫폼 민감도 라우팅 | `LLMAdapter` 교체 (6-3절) |
| **인덱스 갱신** | 수동 1회 | 화면 배포 파이프라인 훅 | 신규 |

**바뀌지 않는 것:** `MenuRouter`, `PII 경계`, `AuthGate`, `ImpactAnalyzer`, `Audit Log`, 3계층 분기. 즉 **아키텍처 전체가 그대로 이관된다.**

### 6-6-2. 크롤링이 실제로는 불필요한 이유

은행은 이미 화면·업무 목록을 내부에 갖고 있다. KB 인터넷뱅킹의 `page=C030037` 같은 **화면 ID 체계가 곧 메뉴 마스터**다. 크롤링은 그 마스터를 *외부에서 본 그림자*일 뿐이다.

그 증거가 우리 데이터에 남아 있다 — 크롤링 결과에 `본문 바로가기`·`English` 같은 **UI 크롬이 섞여 있다.** 내부 카탈로그를 직접 읽으면 이런 잡음이 원천적으로 없고, 각 항목에 화면 ID·권한 등급·소관 부서가 이미 붙어 있다.

> **프로토타입이 크롤링을 쓴 것은 외부인이 접근 가능한 유일한 대역이기 때문이지, 이 방식이 옳아서가 아니다.**

### 6-6-3. 발화 변형은 지어내는 것이 아니라 이미 있다

프로토타입은 LLM으로 발화를 생성했다. 실제로는 **훨씬 좋은 것이 이미 쌓여 있다.**

| 로그 | 무엇이 들어 있나 | 왜 최적인가 |
|---|---|---|
| **챗봇 실패 로그** | "찾을 수 없어요"가 나간 질문 전체 | **정확히 우리가 풀려는 질문들의 목록** |
| 앱 검색어 무결과 로그 | 검색창에 쳤는데 결과가 0건이던 단어 | 사용자가 쓰는 실제 어휘 |
| 콜센터 STT | 전화로 한 말 그대로 | 가장 막연한 형태(L4)의 원본 |
| 민원 텍스트 | 글로 쓴 불만 | 문제 상황의 맥락까지 포함 |

**챗봇 실패 로그가 핵심이다.** 기존 시스템이 답하지 못한 질문의 목록이 곧 우리 서비스의 정답지다. 우리가 생성한 21,000개는 그 로그가 들어올 자리를 미리 만들어둔 것이며, 실제 배포 시 로그로 교체하면 라우팅 정확도가 올라간다.

### 6-6-4. ★ 재학습 2주 문제가 여기서 사라진다

기존 intent 분류 챗봇은 **새 상품·약관이 나올 때마다 의도를 다시 학습시켜야 하고, 현장 반영에 통상 2주가 걸린다.** 그동안 고객은 계속 "찾을 수 없어요"를 듣는다.

우리 구조는 학습이 아니라 **인덱스**다.

```
새 화면·상품 배포
   → 메뉴 카탈로그에 항목 추가 (은행 기존 프로세스)
   → 배포 파이프라인 훅이 임베딩 1건만 계산
   → 인덱스 반영 완료
```

**모델 재학습이 없다. 임베딩 1건이면 끝난다.** 배포와 동시에 반영되므로 공백이 발생하지 않는다. 이것이 intent 분류 대비 구조적 우위다.

### 6-6-5. 단계별 도입

| 단계 | 범위 | 검증 지표 |
|---|---|---|
| **1단계 — 읽기 전용** | Layer 1 라우팅만. 실행 없음 | 라우팅 커버리지, "찾을 수 없어요" 발생률 감소폭 |
| **2단계 — 조회 개방** | Layer 2 추가. 조회계 API 연동 | 콜센터 인입 감소, 창구 방문 사유 변화 |
| **3단계 — 실행 개방** | Layer 3 추가. **리스크 등급이 낮은 업무부터** | 실행 성공률, 취소·이의 제기 건수 |
| **4단계 — 채널 확장** | 전화(어르신전용 1644-3308) ARS 대체 | 평균 통화시간, 상담원 연결 비율 |

**3단계의 순서가 중요하다.** 모든 업무를 한꺼번에 열지 않는다. 되돌릴 수 있는 업무(자동이체 해지, 제증명 발급)부터 열고, 되돌릴 수 없는 업무(이체, 한도 증액)는 마지막에 연다. 이 등급 판정은 은행의 기존 리스크 관리 체계를 따른다.

### 6-6-6. 거버넌스

- **도구 등록은 승인 대상이다.** 어떤 업무를 L2(조회)로 열고 L3(실행)로 열지는 개발자가 아니라 리스크 부서가 정한다.
- **감사 로그는 보존한다.** 어떤 발화가 어떤 도구를 호출했고, 누가 인증했는지 전건 기록한다. 프로토타입의 `Audit Log`가 그 원형이다.
- **모르면 진행하지 않는다.** 부수효과를 확인할 수 없으면 실행을 차단하는 원칙(4-5절)은 실제 서비스에서 더 엄격하게 적용된다.

### 6-6-7. 정직하게 남는 미지수

외부인으로서 확인할 수 없는 것을 명시한다.

- 내부 화면 카탈로그의 **실제 형태와 접근 방식**
- 계열사 간 데이터 공유의 **규제 범위** — 마이데이터 동의 기반으로 어디까지 가능한지
- 실행계 API의 **멱등성 보장 수준** — 재시도 시 중복 실행 위험
- 콜센터 STT 로그의 **개인정보 처리 절차**

이 항목들은 1단계(읽기 전용) 도입 과정에서 확인되며, 그전까지 실행계는 열지 않는다.

## 6-7. KB스타뱅킹에 어떤 기술로 붙이는가

프로토타입은 브라우저에서 도는 정적 사이트다. KB스타뱅킹은 네이티브 앱이다. **이 간극을 메우는 기술 경로를 명시한다.**

### 6-7-1. 배치 형태 — 앱 내 웹뷰 모듈

KB스타뱅킹은 코어 거래는 네이티브, 상품·공지·일부 업무는 웹뷰인 **하이브리드 구조**다(국내 은행 앱의 표준 형태). 본 서비스는 **앱 내 웹뷰 모듈**로 편입한다.

```
KB스타뱅킹 (네이티브)
   └─ 「지문까지」 웹뷰 모듈          ← 대화 UI · 프로토타입 코드가 그대로 이관
        ↕ 네이티브 브릿지
      기존 생체인증 모듈 · 세션 토큰 · 딥링크
        ↕ HTTPS (내부망)
      오케스트레이터 서버 → KB GenAI 플랫폼 · 벡터 검색 · API 게이트웨이
```

**웹뷰를 고른 것은 편의가 아니라 요구사항에서 따라 나온 결론이다.** 네이티브로 구현하면 메뉴가 하나 추가될 때마다 앱 스토어 배포가 필요하고, 그 순간 6-6-4절에서 없앤 **"반영까지 2주"가 되살아난다.** 웹뷰라야 인덱스·프롬프트를 앱 재배포 없이 갱신할 수 있다.

### 6-7-2. 계층별 기술 대응

| 계층 | 프로토타입 | 실제 KB |
|---|---|---|
| 클라이언트 | 정적 HTML/JS (GitHub Pages) | **KB스타뱅킹 앱 내 웹뷰 모듈** |
| 인증 | 화면 버튼 클릭 | **네이티브 브릿지 → 기존 생체인증 모듈** |
| 라우팅 인덱스 | 브라우저가 JSON 전체 다운로드 | **서버 사이드 벡터 검색** |
| LLM | Vercel 프록시 → 외부 상용 API | **내부망 KB GenAI 플랫폼** |
| 업무 실행 | 더미 함수 | **내부 API 게이트웨이 / 전문 인터페이스** |
| 세션 | 없음 | 앱이 이미 보유한 로그인 세션 재사용 |
| 배포 | GitHub Pages | 은행 내부 CI/CD |

**인덱스가 서버로 가는 이유:** ① 메뉴 갱신 시 앱 배포 없이 반영 ② 고객 등급·보유 상품별로 **볼 수 있는 메뉴가 다르므로** 권한 필터링이 필요하다. 클라이언트에 전체 인덱스를 내리면 이 둘 다 불가능하다.

### 6-7-3. 인증 브릿지

웹뷰↔네이티브 인증 연결은 은행 앱의 **기존 표준 패턴**이며 새로 발명할 것이 없다.

```
웹뷰: 실행 계획 생성 (planId)
   ↓ JS Interface(Android) / WKScriptMessageHandler(iOS)
네이티브: 기존 생체인증 모듈 호출 → 지문 확인
   ↓ 인증 결과 + 서명 토큰 반환
웹뷰: AuthGate.issue(planId) 자리에 이 토큰을 넣는다
   ↓
서버: 토큰 검증 후에만 실행 API 호출
```

프로토타입의 `AuthGate.issue()`는 **이 브릿지 호출로 교체되는 단 한 지점**이다. 토큰 검증·1회용·계획별 격리 로직은 그대로 남는다.

### 6-7-4. ★ 새로 만들어야 하는 것은 이것뿐이다

실현 가능성의 핵심 논거는 **KB가 이미 대부분을 갖고 있다**는 점이다.

| 구성요소 | 상태 |
|---|---|
| 생성형 AI 플랫폼 | ✅ **이미 있음** — KB-GPT, KB GenAI 플랫폼(수백억 투자, 2025 가동) |
| 화면·메뉴 마스터 | ✅ 이미 있음 — 화면 ID 체계 |
| 생체인증 모듈 | ✅ 이미 있음 |
| API 게이트웨이 | ✅ 이미 있음 |
| 웹뷰 컨테이너 | ✅ 이미 있음 — 앱이 하이브리드 |
| 계열사 연계 | ✅ 이미 있음 — 6개사 80여 서비스 슈퍼앱 |
| **라우팅 인덱스** | 🔨 **신규** |
| **3계층 오케스트레이터** | 🔨 **신규** |
| **부수효과 분석기** | 🔨 **신규** |

> **신규 개발은 세 개뿐이고, 나머지는 이미 있는 것을 잇는 일이다.**
> 그리고 그 세 개가 정확히 본 프로토타입에서 동작을 검증한 부분이다.

### 6-7-5. 단계별 기술 도입

| 단계 | 기간 | 기술 범위 | 검증 |
|---|---|---|---|
| **PoC** | 1~2개월 | 사내망 웹 + 더미 API + KB GenAI 연결 | 라우팅 커버리지 재측정(내부 카탈로그 기준) |
| **파일럿** | 3개월 | 웹뷰 모듈 + **조회 API 3~5개** + 직원 대상 | 응답시간, 의도 이해율 |
| **확대** | 6개월 | 실행 API 추가 (되돌릴 수 있는 업무부터) | 실행 성공률, 이의 제기 건수 |
| **정식** | — | 전 고객 + 전화 채널(1644-3308) | 콜센터 인입 감소, 창구 방문 사유 변화 |

**파일럿을 직원 대상으로 하는 이유:** KB-GPT가 이미 직원용으로 운영 중이므로, 같은 사용자층에서 검증한 뒤 대고객으로 여는 것이 기존 도입 경로와 일치한다.

### 6-7-6. 성능·비용 추정

| 항목 | 추정 | 근거 |
|---|---|---|
| 벡터 검색 | 밀리초 단위 | 2,655건 × 256차원은 매우 작은 인덱스 |
| LLM 호출 | 턴당 1~2회, 응답 2~3초 | 의도 이해 + 툴 선택만 수행 |
| 모델 규모 | **7B급으로 충분할 가능성** | 생성이 아니라 분류·선택 (6-4절) |
| 캐싱 | 동일 발화 반복은 캐시 히트 | 상위 질문이 집중되는 분포 |

**모델 규모가 작아도 된다는 점이 비용과 망분리를 동시에 해결한다.** 대형 모델이 필수인 설계였다면 내부망에서 애초에 돌릴 수 없다.

### 6-7-7. 데모가 증명한 것과 증명하지 못한 것

정직하게 구분한다.

| 증명한 것 | 증명하지 못한 것 |
|---|---|
| 막연한 발화 → 의도 이해가 실제로 된다 | 내부 API와의 실연동 |
| LLM이 스스로 도구를 고른다 | 실제 트래픽 규모에서의 성능 |
| 계열사 경계를 넘어 라우팅된다 | 권한별 인덱스 필터링 |
| 인증 없이는 실행이 구조적으로 불가능하다 | 네이티브 브릿지 실장 |
| 개인정보가 LLM에 가지 않는다 | 내부망 LLM에서의 정확도 |

오른쪽 항목들은 **은행 내부 접근 권한이 있어야 검증 가능**하며, PoC 단계의 목표가 정확히 그것이다.

## 7. 평가·검증

*iM판에 없던 섹션이며, 기술 적정성 20점의 핵심이다.*

### 7-0. ★ Layer 1 커버리지 검증 — "아무 질문 해도 안 되면"에 대한 답

**전수 자동 검증 루프.** 구현 후 "물어봤는데 안 되네"를 없애는 절차다.

```
1. 크롤링한 2,655개 메뉴를 정답 집합으로 삼는다
2. 각 메뉴마다 발화 변형 8개를 LLM으로 생성  → 약 21,000개
   · 절반(4개)은 인덱스에 넣어 "학습"시킨다
   · 절반(4개)은 인덱스에 넣지 않고 "시험지"로 남긴다   ← 중요
3. 시험지 발화를 MenuRouter에 넣는다
4. 원래 메뉴로 되돌아오는가?  →  Top-1 / Top-3 정확도
5. 되돌아오지 못한 메뉴 = 구멍.  목록으로 뽑아 발화 변형을 보강한다
6. 목표치 도달까지 2~5 반복
```

**2번의 분리가 핵심이다.** 인덱싱한 발화로 시험을 보면 100%가 나오고 그건 아무것도 증명하지 못한다. **본 적 없는 발화로 측정해야 진짜 커버리지다.**

**측정 지표**

| 지표 | 의미 |
|---|---|
| **라우팅 커버리지** | 전체 메뉴 중 자기 자신으로 되돌아온 비율 |
| Top-1 / Top-3 정확도 | 정확히 / 3순위 안에 |
| **미커버 메뉴 목록** | 반드시 산출한다. 없으면 보강이 불가능하다 |
| 계열사 오분류율 | 은행↔카드↔증권을 잘못 보낸 비율 |

**데모 중 실패 로그도 같은 루프로 돌린다.** "아무 말이나 시켜보세요"에서 실패한 발화는 자동 수집되어 다음 라운드의 보강 대상이 된다.

### 7-1. Layer 2 평가셋

5개 업무 × 8개 발화 변형 = **40개**. 막연함의 정도로 층을 나눈다.

**업무당 층 배분:** L1 1개 / L2 2개 / **L3 3개** / **L4 2개** — 막연형·하소연형에 6할 이상을 배정한다.

| 층 | 예시 | 기존 챗봇 |
|---|---|---|
| L1 명령형 | "카드 해지해줘" | ✅ |
| L2 구어체 | "이 카드 안 써, 없애줘" | 🟡 |
| **L3 막연형** | "세금 낼 때 뭐 필요하지?" | ❌ "찾을 수 없어요" |
| **L4 하소연형** | "통장에서 돈이 자꾸 빠져나가" | ❌ |

**L3·L4가 이 서비스의 존재 이유다. 여기서 격차가 벌어져야 한다.**

### 7-2. 측정 표 (기획서 수록)

```
                     의도이해율   툴선택정확도   L3·L4 이해율
대형 상용 모델           __%          __%           __%
소형 상용 모델           __%          __%           __%
intent 분류 (대조군)     __%           —            __%
```

세 가지를 동시에 증명한다:
- **혁신성** — intent 분류 대비 L3·L4 격차를 숫자로
- **기술 적정성** — 왜 LLM인지를 대안 비교로
- **실현 가능성 + 보안** — **소형 모델로도 동작한다면 온프레미스 전환이 현실적**이라는 근거

**로컬 모델(EXAONE 7.8B) 실측은 기각한다.** 개인 참가 + 7일 제약에서 GPU 환경 세팅에 하루가 소모될 위험이 있고, 실패 시 평가 표에 빈칸이 남아 오히려 감점이다. 대신 **대형 상용 vs 소형 상용** 대조로 "파라미터 규모를 줄여도 성능이 유지되는가"를 실측하고, 온프레미스 후보(EXAONE·Solar)는 **function calling 공식 지원 + 유사 파라미터 규모**를 근거로 논증한다. 기획서에 **"로컬 실측은 향후 과제"**임을 정직하게 명시한다.

### 7-3. 안전성 테스트

- **인증 없이 실행에 도달하는 경로가 존재하는가** → 존재하면 설계 실패
- LLM 강제 실패 시 서비스가 살아있는가 (메뉴 검색 폴백)
- 부수효과 조회 실패 시 실행이 차단되는가

## 8. 데모·발표 구성

목차는 미래에셋 2025 대상작 구조를 따른다 — **1번이 "서비스 시연"**이었다. 문제 정의가 아니라 데모로 연다.

```
1. 시연 (앱 4개 + 전화 1개) — 은행 → 카드 → 은행+증권 → 3사 연금 → 전화
2. 왜 이게 새로운가 — KB 7년간 "실행" 0건, 계열사 경계를 넘은 사례 0건
3. 어떻게 만들었나 — 2계층 구조 + PII 경계 + AuthGate
4. 실제로 되는가 — 커버리지 표 + 평가 표
5. KB는 왜 할 수 있나 — KB-GPT는 이미 있다, 다만 행원만 쓴다
                         그룹 공통 AI 플랫폼에 8개 계열사가 이미 참여 중
```

## ★ "아무 말이나 시켜보세요"가 진짜로 성립한다

iM판에서 이건 도박이었다. 하드코딩 범위를 벗어나면 죽기 때문이다. **2계층 구조에서는 도박이 아니다.**

```
심사위원 즉석 질문
   ├─ Layer 2 대상 → 실제로 실행 준비까지 보여준다
   └─ Layer 1만    → "○○ 계열사 > A > B > C 에 있습니다" + 바로가기
                     (2,655개 안에 있으면 반드시 답이 나온다)
```

**최악의 경우에도 "못 찾겠다"가 나오지 않는다.** 그리고 실패한 발화는 자동 수집되어 7-0절 보강 루프로 들어간다.
